PC常駐だった自動投稿サーバー（server.js）を GitHub Actions に移設したものです。
**PCの電源を切っても、クラウド上で自動投稿が続きます。**

>
> Xが **Original Content Rewards Program** を発表し、同日で **Revenue Sharing（クリエイター広告収益分配）の新規受付を終了**しました。既存メンバーの収益は2026-09-07まで、新プログラムへの申請は2026-09-08から可能です。
>
> **このBotの投稿は、新プログラムの収益対象になりません。** 対象外の条件に「created or posted using **automated means**（自動的な手段で作成・投稿されたもの）」が明記されており、本Botは生成（Claude）・投稿（GitHub Actions）の両方が自動です。応募要件にも「Regularly post original content」が含まれます。

>

## 仕組み

```
GitHub Actions（5分おきに起動。※GitHub都合で遅延・スキップされることがある）
   │
   ├─ 返信期限が来た正解があれば → 元ポストへスレッド返信
   │
   ├─ 直近の投稿スロット（5時47分/6時47分/7時47分/8時47分/10時47分/12時13分/15時47分/17時47分/20時47分）
   │    が未投稿なら、該当する内容（ブリーフィング/豆知識/Pollクイズ/振り返り）を投稿
   │    ※豆知識はストックから取り出すだけでAI生成を伴わない（APIコストゼロ）
   │
   └─ 速報チェック（深夜2:00/4:00・朝9:30〜11:00・午後14〜16時の固定時刻のみ）
        話題が急拡大しているニュースを検知したら臨時投稿（朝の枠は無ければ代わりにクイズ）
```

> 💡 **キャッチアップ方式**: GitHubのcronは正確に毎時動く保証がないため、「起動時刻がスロットと一致したら投稿」ではなく「未投稿のスロットがあれば、遅れてでも投稿する」判定にしています。6時間を超えて遅延した場合は深夜投稿を避けるため見送り、次のスロットから再開します。
>
> 追いかける対象は**直近のスロットと、その1つ前のスロット**です（1回の実行で投稿するのは1件だけで、連投はしません）。1つ前まで見るのは、スロットが1時間刻みで隣接しているため、前のスロットが少し遅れて投稿されるだけで（cron遅延では普通に起こる）**投稿間隔の下限30分が次のスロットの前半を塞ぎ、そこにしか実行機会が無いとそのコンテンツが消えてしまう**からです。実際に2026-07-30、4時台の豆知識が4:59に投稿された結果、5時台の朝ブリーフィングが丸ごと消えました。ただし在庫が潤沢な豆知識が、ブリーフィング等の本命コンテンツを押しのけることはありません。

> 💡 **起動は5分おき・投稿は「解禁時刻」で揃える**: GitHub Actionsのスケジュール実行は混雑時に予告なく間引かれます。しかも間引きの度合いは想定よりずっと激しいことが実測で分かっています。
>
> - 毎時47分の1本だけで運用していた2026-08-05の実測: **1日24回のうち約半数しか起動せず、9スロット中6本しか投稿できず**（00・02・04・07・09・11・15・19・21・23時台の起動が丸ごと欠落）
> - 毎時 2/17/32/47分の4本に増やした後、2026-08-06〜08-07の44時間の実測: **期待176回に対して実際の起動は25回＝約14%、平均間隔は約100分**
>
> 起動時刻のUTC分（49 / 09 / 23 / 13 / 21 / 54 / 18 / 52 …）は一見バラバラですが、すべて「4本のtickのどれかが0〜14分遅れて着火したもの」で説明がつきます。つまり**各tickが独立に約86%の確率で捨てられ、生き残ったものが最大14分遅れて届く**状態です。この影響で2026-08-07は9スロット中4本しか投稿できず（03:12〜09:17の6時間が丸ごと無起動で朝ブリーフィングが消滅）、20時台の夜の振り返りは :47 / :02 / :17 の3tickが連続で間引かれて**42分遅れの21:29**になりました。
>
> tickが独立に落ちているなら本数を増やせば起動回数もほぼ比例して増えるため、起動を**5分おき**（GitHubが許す最短間隔・12tick/時）に引き上げています。実効で約36分に1回まで改善する見込みです。
>
> ただし単純に増やすと、時台に入った最初の実行がそのまま発火して投稿時刻が :00〜:47 の間でばらつき、番組表どおりになりません。そのため各スロットに**解禁時刻**を設け、`SLOT_PROFILES` の `releaseMin`（既定45分）以降でないと投稿しないようにしています。この組み合わせにより、**1スロットにつき :45 以降だけで3回、次の時台まで含めれば12回以上の機会**が生まれ、かつ投稿時刻は :47 前後に揃ったままになります。投稿対象が無い回はAPIを一切呼ばず1秒未満で終了するので、起動を増やしてもコストは増えません（公開リポジトリのためActionsの利用料も無料）。
>
> 昼のクイズだけは12時13分に出す運用のため、`12: { releaseMin: 13 }` として例外的に早く解禁しています（以前あった `13 3 * * *` の専用cronは、5分おきトリガーの 3:15 UTC＝12:15 JST に吸収されたため削除しました）。**解禁時刻はスロット順に単調増加していなければならず**（崩れると直近スロットの判定がずれる）、テストで不変条件として検証しています。

> 💡 **速報チェックは固定時刻方式**: 以前の「N時間おきにチェック」という間隔方式をやめ、経験上ニュースが発生しやすい9つの固定時刻（深夜2:00/4:00・朝9:30/10:00/10:30/11:00・午後14:00/15:00/16:00、いずれもJST）だけをチェックする方式に変更しています。`cloud-bot/post-quiz.mjs` の `BREAKING_CHECKPOINTS` で定義しています。以前はこの9箇所に専用cronを並べていましたが、いずれも :00 か :30 で5分おきのトリガーに含まれるため削除しました。1日の速報投稿上限は、チェック箇所が増えたことに合わせて2回→6回に引き上げています（`BREAKING_MAX_PER_DAY`）。
>
> - **朝の枠（9:30〜11:00）**: 速報が無ければ代わりに軽いクイズを1本投稿します（せっかくのチェック枠を空振りで終わらせない）
> - **深夜の枠（2:00/4:00）**: 情報が少なく誤読しやすい時間帯のため、速報が見つかった場合はAIの自己判定に関わらず必ず30分後に詳細な続報記事も投稿します
> - **午後の枠（14:00〜16:00）**: 速報が見つかった場合、生活への影響が大きいとAIが判断すれば30分後に詳細記事を自動投稿します（下記「速報のフォローアップ記事」参照）

> 💡 **Poll形式**: 12時・17時のクイズはXの投票機能を使い、1タップで参加できるようにしています。生成結果は以前JSONで受け取っていましたが、記事タイトル中のダブルクォートで解析に失敗する事故が3回起きた（2026-07-20/23/31）ため、長文側と同じ**区切り記号方式**に変更しました。本文・正解文・選択肢をそれぞれ独立したブロック／行で受け取るので、中にどんな記号や改行が入っても壊れません。選択肢が25文字を超える等でPollとして投稿できない場合は、自動でテキスト形式に切り替わります（投稿自体は止まりません）。

> 💡 **情報収集は自前検索（`SEARCH_MODE=self`・既定）**: ブリーフィング・振り返り・クイズの元ネタは、Anthropicの`web_search`ツールではなく**Tavilyで先に検索し、結果をまとめて1回だけモデルに渡す**方式です。
>
> ツール利用は仕様上ターンごとに全文脈を再送するため、入力トークンが検索回数のおよそ2乗で膨らみます（実測: 1投稿あたり入力57,113トークン）。
>
> ```
> 1回目 2,000 → 2回目 10,000 → 3回目 18,000 → 4回目 26,000 …合計88,000
> ```
>
> 先に検索して一度だけ渡せばこの再送が消え、**モデルも文章品質も変えずに入力を約6割削減**できます（月4,275円 → 約1,559円の試算）。
>
> - **クエリは種別ごとに固定**（`searchPlanFor`）。このBotが毎日必要とするのは「今日のニュース」であって日替わりの調査課題ではないため、検索語をモデルに考えさせる中間呼び出しは不要です。Tavilyの`topic: "news"` / `days: 1`で当日分に絞っています。
> - **上位2件は全文、残りはスニペット**（`SEARCH_FULLTEXT_COUNT` / `SEARCH_CONTEXT_MAX_CHARS`）。総量に上限を設けて入力トークンの上振れを防いでいます。
> - **出典URLが正確になります**: クイズの`sourceUrl`は、モデルの記憶からではなく検索結果の`URL:`行をそのまま転記させています。
> - **落ちてもBotは止まりません**: `TAVILY_API_KEY`が未設定・検索が失敗・結果が空のいずれでも、自動的に従来の`web_search`ツールに退避します（`cloud-bot/test/search-fallback.test.mjs`で検証）。プロンプトの情報源の指示文も`researchLine`でモードに連動させており、「検索しろと書いてあるのに検索結果が無い」状態は起きません。
> - **切り戻し**: `SEARCH_MODE=tool` で従来方式に戻ります。手動実行（workflow_dispatch）の`search_mode`と`dry_run`を組み合わせると、同じ日の内容を両モードで生成して読み比べできます。
> - **コストの実測**: 毎回の実行ログに `🔢 claude-sonnet-4-6 入力… 出力… 検索…回 (selfモード)` が出ます。推定ではなく実測で削減効果を追えます。
>
> ⚠️ **速報関連（`generateFeature` / `generateFollowUp`）は従来のツール方式のままです。** `checkBreaking`のみ2026-08-06にX API Trends（$0.010/回）を先に取得してから探索する方式へ変更し、`BREAKING_ENABLED`も`true`に戻して再開しました。トレンド取得が失敗した場合は従来のオープンエンド探索にフォールバックします。`generateFeature`/`generateFollowUp`はまだ移行対象外です。

> 💡 **月間投稿数の安全上限**: `MONTHLY_POST_LIMIT`（既定450件）に達すると、その月は投稿を自動で見送ります。X無料プランの投稿数上限を超えないための保険です。

> 💡 **投稿間隔の下限**: スロット投稿・速報投稿（新規のトップレベル投稿）は、前回の投稿から最低30分空けます。手動テスト（force_post）で直後にスロット投稿と重なった場合や、速報検知がスロット投稿と同じ実行内で見つかった場合でも、間を空けずに2件同時投稿されることはありません（見送られた分は次回の実行で再試行されます）。正解のスレッド返信はこの制限の対象外です。

> 💡 **速報のフォローアップ記事（自動・1回のみ）**: 決済障害・交通障害など「生活に直結する話題」の速報は、AIが自己判定して30分後に詳しい続報記事（原因・影響・対処法まで）を自動投稿します（自動フォローアップはコスト・運用面から30分後の1回のみ）。投稿間隔（30分）や月間上限に抵触しそうな場合は、無理に投稿せず時間を後ろにずらすか（最大2時間分・それでも空かなければ中止）、見送ります。前回の速報から本質的に新しい情報が無い場合は、続報自体を出しません。その日扱った速報・続報は、20時の夜の振り返りでも他の話題より多くの問題数を割いて深掘りされます。
>
> 💡 **速報投稿をIssueで通知**: 🚨速報（1回目）が投稿されると、GitHubにIssueが自動作成され通知が届きます（`breaking-news`ラベル）。30分後の自動フォローアップ以上にさらに続報が必要な場合は、Actionsの手動実行（workflow_dispatch）で`BREAKING_TOPIC`または`FEATURE_TOPIC`を指定して手動で作成してください。

> 💡 **投票結果を正解返信に反映**: 12時・17時のPollクイズは、正解をスレッド返信する際にその時点の投票結果（例: 「📊 投票結果: A案 62% / B案 38%」）を先頭に付けます。X無料プランは投票結果の読み取りAPI枠が少なく、取得に失敗することがありますが、その場合は投票結果なしの通常の正解返信にフォールバックします（投稿自体は止まりません）。
>
> 正解返信が失敗した場合は次回の実行で再試行しますが、**元投稿が削除された等の恒久的なエラーなら即座に、一時的なエラーでも4回で諦めて**キューから外します（放置すると毎時の実行で永久に再試行し、少ない読み取り枠を食い続けるため）。投票結果の取得も、実際に投稿を試みる時だけ行います。

> 💡 **既知の誤記の自動修正**: 人名などの固有名詞は投稿後に直せないため、プロンプトでの注意に加えて、投稿直前に機械的にも直します（`post-quiz.mjs` の `KNOWN_MISSPELLINGS`）。実際に「高島首相」と誤記したまま投稿された事故があったための保険です。修正が働くとログに「✏️ 既知の固有名詞の誤りを投稿直前に修正しました」と出るので、その場合はプロンプト側も見直してください。**内閣総理大臣が交代したらこの表も更新が必要です。** 誤りだと文脈に関係なく断定できるものだけを登録し、「高島屋」「高島さん」のような実在の別語は書き換えません（役職を伴う場合だけを対象にしています）。

> 💡 **投稿履歴の記録**: 投稿するたびに `state.json` の `postHistory`（最新30件・tweetId/種別/カテゴリ/本文冒頭/投稿時刻）に記録します。Pixelのクイズボットアプリの「☁️ クラウドBot」カードから、この履歴とタップで各投稿を開くリンクを確認できます。
>
> 💡 **豆知識記事のストック（`cloud-bot/trivia-stock.json`）**: 事前に書いた記事をAI生成を介さず**1日5本**（6時47分／7時47分／8時47分／10時47分／15時47分）投稿する仕組みです。投稿位置は`state.json`の`triviaNextIndex`で配列の先頭から順に管理しています。
>
> - **なぜ5本か**: 投稿量がそのまま露出に効くためです。豆知識はストックから取り出すだけでAnthropic APIを一切使わないため、**投稿を増やしてもAPIコストが増えません**。1日11投稿・月約340件で、月間投稿の安全上限450件の範囲に収まります。
>
>   ⚠️ この本数設計のもとになっていた「収益化の壁は直近3ヶ月で500万インプレッション」という前提は、**2026-08-08のプログラム変更で失効しました**（冒頭の警告を参照）。500万という数字自体は旧Revenue Sharingの条件として正しかったものですが、新プログラムでは基準も数え方も変わっており、そもそも自動投稿は対象外です。**露出量を増やす目的で本数を維持する根拠は、いまのところ失われています。**
>
> - **追加方法（推奨・JSON編集不要）**: リポジトリの **Issues → New issue → 「🐹 豆知識記事を追加」** を選び、本文欄に記事を貼り付けて送信するだけ。ワークフロー（`.github/workflows/trivia-intake.yml`）が自動で`trivia-stock.json`の末尾に追加し、Issueにコメントして自動でクローズします。スマホのGitHubアプリからでも同じ手順で投稿できます。
> - **直接編集する場合**: 文字列の配列（例: `["1本目の本文...", "2本目の本文..."]`）を直接GitHub上で編集してもよいですが、**必ず配列の末尾に追加**してください（途中に挿入したり過去分を削除すると投稿順がずれます）。
>
> どちらの方法でも、ストックが尽きた日は投稿を見送ります（エラーにはなりません）。
>
> - **残りが少なくなるとIssueで通知します**: 未投稿の残りが**8本（`TRIVIA_LOW_STOCK`・約1.5日分）以下**になると、`trivia-stock-low` ラベルのIssueを1件だけ作成します。補充されて残りが増えると、次の実行で自動的にクローズされます。在庫切れは投稿が無言で減るだけでエラーにならないため、ログを見ていない限り気づけません（2026-08-05に在庫が尽きて豆知識が約12時間止まり、指摘を受けるまで気づけませんでした）。残量は毎回の実行ログの `📚 豆知識ストックの残り: N本` でも確認できます。
>
> - **投稿できない記事は自動でスキップされます**: 曜日表記や重複などでXに投稿できない記事に当たった場合、その記事を飛ばして次へ進みます（インデックスを進めずに止まると、以後すべての豆知識スロットが同じ記事で失敗し続けて永久に停止するため）。スキップした記事はログに冒頭60文字が出ます。ただしX API側の一時的な障害（5xx）の場合は記事を温存し、次回の実行で同じ記事を再試行します。
> - **深夜・早朝（JST 6時前）には投稿しません**: 遅延したスロットを深夜まで追いかけると、露出が取れないまま本数の限られたストックを浪費するため、見送って温存します。スロット投稿全体にもJST5時前のガードがあり、持ち越しの振り返り等が深夜に出ることはありません。
> - **ストックの改変を検知します**: 投稿位置を配列の添字で管理しているため、末尾追加以外の操作（並べ替え・過去分の削除・全体の再生成）をすると投稿順が静かにずれます。直前に投稿した記事の冒頭を`state.json`の`triviaLastPostedHead`に控えており、位置がずれていればログに警告を出します（自動では直しません）。
> - なお豆知識は永続ネタのため、曜日の一致チェック（ニュース系の「今日は○曜日です」の誤りを防ぐ仕組み）の対象外です。曜日の語源のような話題も安全に扱えます。
>
> - **書き方の基準**: [`cloud-bot/trivia-style.md`](trivia-style.md) が正本です。3部構成（見出し／本文／「朝礼で使うなら:」）と事実確度のルールをここにまとめています。手でIssueから追加する時もこれに沿って書いてください。
>   「朝礼で使うなら:」は一言コメントではなく、**挨拶から締めまで読み上げればそれで終わる台本**にします（3〜5文・150〜220字）。
> - **自動補充（毎日）**: ストックが減ると、**PC側のClaude定時タスク `trivia-refill`**（毎日 13:00）が
>   **未投稿の残りが30本**になるまで記事を生成し、`trivia-stock.json` の末尾に追記してmainへpushします。
>   **cloud-bot側では生成しません**（Anthropic APIは使いません）。手順の正本はPC側の `C:\TriviaRefill\手順書.md`。
>   補充した記事は配列の末尾に入るため、実際に投稿されるのは在庫が掃けた**約6日後**です（見直す余裕は十分あります）。
>   実行時刻はもともと22時40分でしたが、**PCが落ちていて3日連続で補充が飛び、在庫が残り1本まで枯渇した**ため
>   （2026-07-30〜08-01）、PCが起動している時間帯に寄せて13時00分へ変更しました。
>
> 消費は1日5本（6/7/8/10/15時台）。毎日補充なので平常時は1回あたり5本前後、**1回の上限は10本**です。
> 上限10本は、実行が数日飛んだあとに追いつくための枠であって、埋めるべき目標ではありません
> （質の伴わない記事で本数を埋めないことを、手順書とタスクのプロンプト両方に明記しています）。
>
> **目標は当初16本でしたが、2026-08-05に30本（約6日分）へ引き上げました。**
> 16本は1日5本消費で3.2日分しかなく、補充が数日飛べば必ず枯渇します。実際に2回枯渇しました
> （8/01に残り1本、8/05に残り0本で約12時間スロットが空振り）。補充側はPC上のClaude定時タスクで、
> クラウドと違い実行を保証できないため、**在庫の厚みで吸収する**方針にしています。
> 在庫が切れてもエラーにはならず、その枠の投稿を見送るだけですが、その分だけ露出が減ります。

- 出題履歴（直近のトピック・書き出し・速報の見出し）を `state.json` に記録し、重複を避けます
- Pixelのクイズボットアプリ（PWA）はこれまで通り、監視・手動投稿・収益化トラッカーとして併用できます

## 初期設定（1回だけ・スマホのブラウザでも可能）

### 1. Secrets の登録

GitHubリポジトリの **Settings → Secrets and variables → Actions → New repository secret** で、以下の6つを登録します:

| Name | 値の取得場所 |
|---|---|
| `ANTHROPIC_API_KEY` | console.anthropic.com → API Keys（`sk-ant-` で始まる） |
| `TAVILY_API_KEY` | app.tavily.com → API Keys（`tvly-` で始まる）。**未設定でも動きます**（従来のweb_searchツールに自動退避）が、設定するとAPIコストが約6割下がります |
| `X_API_KEY` | developer.x.com → プロジェクトのアプリ → Keys and tokens → API Key（Consumer Key） |
| `X_API_SECRET` | 同上 → API Key Secret（Consumer Secret） |
| `X_ACCESS_TOKEN` | 同上 → Access Token（**Read and Write権限**で発行したもの） |
| `X_ACCESS_TOKEN_SECRET` | 同上 → Access Token Secret |

> 💡 **Tavilyの無料枠について**: 使用量は1日4投稿 × 2〜3クエリで**月360クエリ程度**です。無料枠（執筆時点で月1,000クレジット）に収まる想定ですが、枠と課金体系は変わることがあるので登録時に確認してください。枠を使い切っても、検索が失敗した扱いで従来のweb_searchツールに退避するだけで投稿は止まりません。

> 💡 PC側の `.env` に設定していたものと同じ値を使えます。ワークフロー内部では `TWITTER_*` という名前に読み替えていますが、GitHubへの登録名は上記の `X_*` で統一しています。

### 2. テスト実行

1. リポジトリの **Actions** タブ → 左の「Cloud Bot」→ **Run workflow**
2. `dry_run` に✔が入ったまま実行 → ログに生成されたクイズが表示される（投稿はされない）
3. 内容に問題なければ、`dry_run` の✔を外して再度実行 → 実際にXへ1回投稿される
4. Xのプロフィールで投稿を確認。約2時間後の定時実行で正解がスレッド返信される

### 3. PC側の停止

テストが確認できたら、PC側の server.js（と自動投稿に使っていたブラウザ）を停止してください。
以後、定時投稿はすべてクラウド側で行われます。

## 設定の変更

`.github/workflows/cloud-bot.yml` の `env:` セクションのコメントを外して編集します:

| 環境変数 | 既定値 | 意味 |
|---|---|---|
| `ANSWER_DELAY_HOURS` | `2` | 正解返信・Poll投票期間の長さ |
| `MONTHLY_POST_LIMIT` | `450` | 月間投稿数の安全上限（超えると投稿を見送る） |
| `BREAKING_ENABLED` | **現在`true`（稼働中）** | `false`で速報チェックを中止（自動検知・続報・朝9:30〜11:00の代替クイズもすべて停止）。2026-08-06にTrends先読み方式へ変更のうえ再開 |

投稿する時刻（5/6/7/8/10/12/15/17/20時台）を変えたい場合は、`cloud-bot/post-quiz.mjs` 冒頭の `SLOT_PROFILES` を編集してください。分単位でずらしたい場合は該当スロットに `releaseMin` を足します（既定45分。解禁時刻がスロット順に単調増加している必要があり、崩れるとテストが落ちます）。cronは5分おきの汎用トリガーがすべてのスロットをカバーするため、通常は追加不要です。速報チェックの時刻・上限回数を変えたい場合は同ファイルの `BREAKING_CHECKPOINTS` / `BREAKING_MAX_PER_DAY` を編集し、時刻を変更した場合は `.github/workflows/cloud-bot.yml` の対応するcronトリガーも忘れずに変更してください。

> 💡 **取りこぼしたスロットを後から投稿する**: それでも取りこぼした場合は、Actionsの手動実行で `force_slot` に時台の数字（例: `5`＝朝ブリーフィング）を入れ、`force_post` をONにして実行すると、そのスロットの内容を作り直して投稿できます。

## 失敗時の通知

実行が失敗すると、リポジトリに **「🚨 Cloud Bot の実行が失敗しています」というIssueが自動作成**され、GitHubから通知が届きます。Issueに書かれた実行ログのリンクから ❌ で始まる行を確認してください。解決したらIssueをクローズしてください（クローズするまで重複Issueは作られず、再失敗は同じIssueへのコメントで通知されます）。

## 停止方法

- **一時停止**: Actions タブ → Cloud Bot → 右上「…」→ **Disable workflow**
- **再開**: 同じ場所から **Enable workflow**

## 注意事項

- 定時実行（cron）は **mainブランチにあるworkflowだけ**が動きます。ブランチで編集した場合はmainへマージしてください
- GitHub Actions の cron は数分〜十数分遅れるほか、混雑時には起動そのものが間引かれます（実測で約半数）。1スロットあたり4回の起動機会を用意して取りこぼしを減らしています
- このリポジトリはpublicのため、Botのプロンプトと出題履歴（state.json）は公開されます。**秘密情報はSecretsにのみ保存**されるため漏洩はしません
- X APIの利用枠（無料プランは投稿数上限あり）と、Anthropic APIの残高に注意してください
- Xの[自動化ルール](https://help.x.com/ja/rules-and-policies/x-automation)に従い、アカウントの自動化ラベル設定を推奨します
